# 科学智能体与远程实验阅读笔记｜2026-10-19

本期整理5项研究资料，保留原始发表日期；首次入库不等于本日新发表。AI辅助整理，推荐不表示维护者已读；作者报告未独立复现。真实设备、软件执行与回放/仿真实验分别说明。

## 1. Jianmu-Q: Bridging Quantum Field Theory and Quantum Hardware with AI Agents

[原始来源](https://arxiv.org/abs/2610.21942) · [正文](https://arxiv.org/html/2610.21942v1)｜2026-10-15｜v1｜华南师大、RIKEN、KEK等；Xiaolin Wang等

把量子场论问题送上量子计算机，困难不只在写线路。研究者首先要把连续理论变成有限格点模型，再确定边界条件、量子比特编码、待测物理量和状态制备方式；任一步换了约定，最后的数值即使看起来合理，也可能回答另一个问题。Jianmu-Q 将这些跨专业交接分给不同代理，并用结构化记录传递同一套物理定义。输入包括模型、外部状态和观测量；输出除了线路与数值，还保留推导、审查、失败尝试和各阶段决定。

具体过程先检查理论及离散化后的守恒关系，再生成保持相关对称性的状态制备线路和测量线路。线路用 Qiskit 表达；SciPy 的精确对角化和 ITensor 的张量网络计算则从共同的格点定义出发，独立生成参考答案，不读取量子线路结果。确定性运行器负责参数优化、无噪声模拟和数值验收；若随线路深度增加仍不收敛，反馈回到线路设计阶段，有限次重设方案。这里维护的科学状态是哈密顿量、观测量、对称性与近似条件，而不只是聊天记录。全程是代码和专用程序接口，未使用截图GUI或MCP；人提供问题和运行配置，论文未提供逐步人工介入统计。

作者展示 NJL、Schwinger 和二维 Z₂ 规范理论三个案例。Schwinger 案例的两套独立经典参考吻合，增加状态制备深度和时间演化步数后，相关量对精确参考的最大偏差由0.594降到0.00806，支持的是同一有限格点问题的计算一致性。系统随后评估真机可行性，因线路深度或双比特误差预算不合格而跳过该案例提交；这比“所有问题都上机”更能说明资源检查确实改变了动作。另两个案例有 IBM ibm_kawasaki 的真实执行。Z₂ 案例浅线路重建的能隙为8.1483±0.1350，与相同线路无噪声值7.7502相差约2.95个统计标准误；纠错后仍有偏差，不能把模拟收敛写成真机精确验证。作者也将真机数据定位为设备测试，未展示依据这批新测量再次改写科学方案的完整轨迹。

**证据边界：** 有限格点数值一致性不等于连续极限/真机定量准确；未测跨仪器接入人时

**先读：** 第三节、图1、Schwinger案例末段。

## 2. Autonomous Science Bench: Evaluating AI Agents for Autonomous Scientific Discovery

[原始来源](https://arxiv.org/abs/2610.18449) · [正文](https://arxiv.org/html/2610.18449v1)｜2026-10-13｜v1｜Northwestern University；Yibo Wen、Han Liu

科学代理可以碰巧找到一个好材料，也可以拟合出漂亮曲线，却没有学到能迁移的规律。本文因此不给“实验成功”一个笼统分数，而要求同一轮研究同时过两道门：实际选中的设计要达到发现目标，最后提交的预测器还要能排列没有见过结果的设计。作者把六个已发表研究整理成有限预算、多轮选点的任务，代理得到起始数据、候选空间和预算，通过统一 Lab API 下单，读取结果后选择下一轮，最终交付可执行预测器。实验服务独立记账和限制预算，防止代理自己声称已测量或绕开额度。五个任务回放既有实验数据，一个任务使用数字孪生；这些服务没有在本轮获取新的现实测量。

八种代理与模型配置各跑六个任务、每项三次，共144次，31次同时过关；最佳配置的67%来自18次中的12次，不是144次总体成功率。最难的矫顽力任务仅3/24成功。更有解释力的是113次失败中，25次只缺发现、30次只缺学习、58次两项都缺：单一总成功率会掩盖“找到好点却没学会”与“预测不错却没找到目标”的区别。作者还用多种数据划分审计静态选择和零测量预测捷径；这些是任务设计的校准条件，因此难度并非原研究流程的中立抽样。

**证据边界：** 公开数据潜在记忆、任务按捷径审计校准、未含现场漂移和样品失败

**先读：** 2.4/2.6与表5，附录矫顽力任务。

## 3. Probe-and-Resume: When and How to Evaluate Agent Execution

[原始来源](https://arxiv.org/abs/2610.21088) · [正文](https://arxiv.org/html/2610.21088v1)｜2026-10-15｜v1｜Columbia University；Jiakai Xu等

长程计算任务里，代理说“做完了”不代表文件、服务和数据已经符合要求。只看操作文字还不够：关键状态可能没有进入轨迹，评价者也很难从中途几步判断最终能否成功。作者先研究分支搜索和评价模型，发现给代理提供快照工具，或在中间节点反复评分，并没有明显提高这一组终端任务的成功率。由此提出更集中的检查时机：等执行代理明确宣称完成，再让另一代理动手验证。

检查者获得当前状态和初始状态各自的一份隔离副本，可以读写文件、运行程序、安装依赖，甚至执行会破坏副本的测试；初始副本用于判断原文件是否保留、恢复是否正确等要求。检查结束只把证据和拒绝理由交回，副本内改动全部丢弃。执行者从原来声称完成的现场继续修正，保留已有工作，而非被迫从头再来。实现依赖可快照的容器和终端命令，是代码层面的计算机使用；没有科学仪器，也没有现实物理状态回滚。

在 Terminal-Bench 2.1 的89项任务上，每项五次，用相同 GPT-5.6 Luna 比较，首次完成即提交的成功率为63.4%，Probe-and-Resume为72.4%；最终由任务验收器判定，检查代理看不到隐藏验收答案。计算预算计入执行、检查、快照和分叉，验收评分本身不计时。中途蒙特卡洛树搜索约64.0%，但这一组搜索比较排除了18次无法评分的试验，不能把各百分比都解释成完全相同分母的无条件实验。新方法在30/89项任务提高通过率，在1项退步；它仍会错拒绝，成功来自执行与检查共同修正，并非检查者已完全可靠。作者与另一CLI系统的成本比较还涉及不同运行框架，不能直接当通用省钱结论。

**证据边界：** 物理状态不能分叉；检查仍会错拒；其他CLI成本比较含框架差异

**先读：** 第5节与表3、初始状态副本消融。

## 4. ELISA: A Bayesian X/γ-ray Spectral Analysis Toolkit

[原始来源](https://arxiv.org/abs/2610.14587) · [正文](https://arxiv.org/html/2610.14587v1)｜2026-10-10｜v1｜中科院高能物理研究所等；Wang-Chen Xue等

高能天文探测器记录的是不同能道中的计数，不是天体直接发出的光谱。仪器响应和背景会改变这些计数，直接反演往往没有稳定唯一解。ELISA 采用正向建模：研究者给出天体光谱假设，把它通过探测器响应折算成预计计数，再同观测数据比较。本文试图把通常分散在建模、参数采样、诊断和模型选择程序中的步骤统一到一个Python工具包，减少分析过程换工具时丢失统计假设的风险。

输入包括光谱、背景及响应数据；研究者选择模型、先验和拟合范围，工具把共享参数与各数据集的专属参数关联起来，按计数及背景类型选择似然。JAX支持自动微分和加速，使采样器利用参数梯度探索可能解。拟合后除了参数区间，还输出链是否充分混合、有效样本量和预测诊断；研究者据此决定是否继续采样、改模型或承认参数无法约束。这里的反馈是分析者的判断，不是自主调度望远镜；本轮展示的是既有 Insight-HXMT 蟹状星云观测，未取得新曝光。

案例将三个探测器数据共同拟合，分组后共131个拟合能道，模型是吸收修正的幂律。作者在指定M1 Max CPU配置上更换随机种子重复100次，ELISA/NUTS每次约12–16秒，XSPEC的Goodman–Weare集合采样约80–110秒；前者有效样本量约一万，后者不超过一千，作者据此报告该案例每秒有效样本量约百倍的差异。这个指标表示统计信息获取效率，不是所有天文计算都快百倍。正文虽概述“匹配设置”，随后列出的链/行者、预热和保留步数并不相同，且采样算法也不同，因此不能把增益单独归因于软件实现。模型比较又显示，加入高能截止参数后的预测准则差约1.2、标准误约1.4，改进没有超过自身不确定性，不能因为模型更复杂就宣称发现了截止特征。

**证据边界：** 正文匹配设置概述与列出的链/步数不完全一致，算法不同；不可隔离归因或普遍百倍

**先读：** 第五节诊断与第六节模型比较。

## 5. Easy remote observations using web interfaces: controlling an Italian telescope from Japan, and more

[原始来源](https://arxiv.org/abs/2501.07997) · [正文](https://arxiv.org/html/2501.07997v1)｜2025-01-14｜v1｜INAF、日本国立天文台等；Davide Ricci等

这篇回答一个容易被“浏览器即可操作”掩盖的问题：浏览器后面究竟已经做好了多少仪器适配？作者要把意大利 OARPAF 米级望远镜变成可远程使用的设施。原设备有不同控制方式：望远镜用专有命令，圆顶经过设备驱动，CCD、滤轮、监控相机和电源又有各自HTTP接口。最初利用ASCOM Remote把设备功能暴露为REST API，再建立Python控制层，把多设备常用操作组织成观测块，最后提供共同API和网页。后来还为望远镜与圆顶改写接口以减少中间Windows机器的依赖，说明接入成本发生在使用者看到网页之前。

在这套系统里，网页定期接收带状态的信息，操作者通过API发出控制请求，取得的FITS天文图像由网页内JS9显示。观测块可以调用预写程序，但每个天文台仍需按自己的设备定制模板，不能把配置文件示例理解成任意仪器零工程接入。作者也保留Python与REST调用方式，因此GUI和API是同一底层能力的不同入口，不是互斥路线。本文没有LLM、Computer Use代理或MCP，决策和操作由人完成。

最清楚的现场案例是日本高中学生从教室连接意大利真实望远镜。学生先选定M13球状星团、多滤镜观测目标和可见性条件，再远程开启相关装置、指向、调焦，在V和I滤镜各取得三帧新图像。随后用ds9对约200颗恒星做粗略测光，借助Simbad已有星等选择标准星，再把颜色—星等图与文献中的另一星团比较。这里真实新测量、图像查看、目录查询和科学分析确实形成跨应用人工工作流；原文没有展示测光结果触发下一轮改变曝光或目标。它证明这次远程使用可行，没有对照实验足以证明更快、更准，摘要提到的专业凌星用途也没有在正文中同等展开。HTML丢失部分曝光及传输时间单位，本期不把这些数值当精确时延证据。

**证据边界：** 旧能力证据非当前开放服务；HTML时延/曝光单位丢失不引用；接入人时/资格/价格未知

**先读：** 第二节控制层次、第三节学生案例。
